A cone course, one token at a time

How far can a decision model drive?

A simulated Corolla, an autocross course and a camera. About once a second, rev asks a served vision model ten left-or-right questions about what the camera sees and reads one token back from each. A controller drives to where the answers say the course goes.

The setup follows DrivingBench: the same camera mount, cone density, walking pace, and the rule that a touched cone ends the run.

Results

How rev drives

The model never steers. It says where the course is, and everything about driving belongs to a controller that can be tested without it.

1

Five views

From the camera at the top of the windshield: the view ahead and views turned 15° and 30° each way, cut from the wide camera.

2

Ten questions

For each view and its mirror image: is the middle of the lane left or right of the middle of the picture? One token each, all at once.

3

A direction

The mirror cancels any lean to one side; a fitted linear readout turns the five answers into the course's direction.

4

A point on the ground

Fixed in the world where the picture was taken, far enough ahead to still be ahead when the answer lands, a second later.

5

A controller

Pure pursuit steers to the point; the model picks the speed as a digit, 0 for stop to 9 for the ceiling.

Findings

Each one measured; the full record, including everything that did not help, is in DECISIONS.md.

The harness is not the limit

Given the course's true direction instead of the model's, the same controller at the same one-second latency finishes every course without touching a cone.

It cannot see a tight corner from inside it

At a 90° corner the model says "left" with the same probability, 0.73, for every view and every mirror image. Asked in plain chat, it answers the course proceeds straight ahead.

The question decides what can be read

Asked how to turn the wheel, it steers away from the cones in front of it, the wrong way in a bend (r = −0.85). Asked whether the lane's middle is left or right of the picture's, it reads the direction to 3.9°.

Less input reads better

DrivingBench's full inputs, two cameras, a long task description and the wheel position, took the error from 3.9° to 6.6°. Extra pictures dilute the one the question is about.

Slower goes further

In a side-by-side test on course 0, a 1.5 m/s ceiling, their pace, took the model 78% of the way round; a 3.5 m/s ceiling, 30%. More answers per metre catch small misreadings before they reach a cone.

Memory did not help

Remembering its own recent answers, even weighted by confidence, locked in its confident mistakes: a quarter of its sure answers are more than 6° off.

Compared with DrivingBench

DrivingBench puts frontier agents in a real car through three tools and lets them reason. revdrive keeps what the model sees and may do as close as a one-token model allows, and gives up the rest.

Replays

Every run is saved as a trace and drawn again: the camera view, the map, the telemetry, and each decision with the picture the model was shown and how far off it was.

Run it

The oracle needs no model. rev and blind need an sglang server serving a Qwen vision model.

# install
uv pip install git+https://github.com/54yyyu/revdrive

# the harness's ceiling: the true direction, the same controller, rev's latency
revdrive run --policy oracle-point --courses 0-9,100 --latency 1.0

# the model, and the model shown grey pictures
revdrive run --policy rev   --courses 0-9,100 --upstream http://HOST:PORT
revdrive run --policy blind --courses 0-9,100 --upstream http://HOST:PORT

# watch it drive, replay a run, or drive it yourself with the arrow keys
revdrive ui --upstream http://HOST:PORT
